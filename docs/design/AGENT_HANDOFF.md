# Cite-Audit Remake · 开发 Agent 交接指令

版本 2.0 · 2026-10-30 · 未来开发执行时使用

## 任务定义

基于本交付包**从零构建** Cite-Audit。它是面向论文作者的整份 BibTeX 核查产品：一次上传生成一个任务，输出每条引用的证据化核验结果、字段差异、正式版建议和安全校订导出。共享知识库以**Article → PublicationVersion → SourceContent**积累已知事实并维护默认推荐版本。

**这是一份将来可交给 Agent 的任务规范。本次交付只更新文档，不修改代码、不推送提交、不创建 PR、不部署。**

## 开发边界：完全 Greenfield

- **不要基于旧实现做增量改造**，不要 import/copy 历史项目业务模块、组件、SQL 或缓存工具；不要建立旧数据迁移、旧 API、旧 UI 或旧状态映射。
- 允许采用经过选择的通用第三方基础库（如 React、shadcn/ui、FastAPI、BibTeX 解析库），它们不是“旧代码依赖”。
- 可以从仓库的干净基线创建独立开发分支，但不得在未经明确开发指令时修改已有 PR 或把旧功能复制进来。新 PR 的创建、合并与发布均由未来开发流程安排。
- 使用 `uv` 管理 Python 项目与 `uv.lock`；前端使用自己的标准包管理锁文件；不要制造多个重复依赖清单。
- 代码以简单、清晰、低封装负担、易读、易测试为首要质量要求；实现具体依赖时先验证维护与授权状态。

## 必须遵守的十项业务不变量

1. 一份 Bib 上传是一个独立 `AuditTask`；再次上传不是特殊“复查”。
2. 原始 Bib 字节不可变，校订必须生成新文件。
3. 三层知识结构：Article / PublicationVersion / SourceContent；推荐指向 Version。
4. 不同数据源描述同一出版记录时归并到一个 Version，不能因小字段差异制造伪版本。
5. 同版本字段可有来源依据地补全与保留冲突；**不同版本之间不得拼接书目字段**。
6. 先判定当前输入真正指向哪个版本，再比对当前版本；推荐版本作为另一个建议维度。
7. 准确预印本 + 存在可靠正式版 = **当前有效，建议改用正式版**，不是原年份/DOI 错误。
8. 作者选择、上次通过结论、未经确认的 Bib 值不进入共享知识事实层。
9. 每条确定性的事实修正可回溯具体来源快照；搜索未命中 ≠ 论文不存在。
10. Mock/人工材料/失败/已过期资料有清楚状态，不得被渲染为已在线核实。

## 交付顺序

按 `DEVELOPMENT_GUIDE.md` 的 M1→M4：新项目骨架与任务 → 三层知识库与引用核验 → 官方论文集与四个完整页面 → 校订导出及端到端验收。各阶段采用小而可验收的提交；每步都应说明测试覆盖、未完成项和真实来源限制。不要为了快速出图而伪造后端证据，也不要只画静态首页。

## 前端执行规范

- 视觉按 00 风格图：低饱和白灰背景、细边框、少阴影、紧凑表格、克制颜色；不要照搬示意数值。
- 界面必须是**任务列表、任务详情、引用核查详情、知识库**四个独立全页；设置是辅助页。
- 引用详情不得简化：当前版本核验、推荐版差异、字段级来源、版本关系、原始 Bib、候选和查询日志都可访问。
- 各按钮需有真实动作；不做装饰性“采纳”“保存到知识库”操作。
- 提供桌面、平板/窄屏和深色模式的可访问性检查。

## 开发验证与报告格式

应交付：新代码、锁文件、建库方案、API 文档、离线 fixtures、自动化测试、真实来源调用测试记录、四张独立页面截图、部署/本地使用文档。没有真实凭据可先做离线集成，但必须明确区分 mock 与真实核验。

每一轮报告采用四段：**本轮实现 / 测试与证据 / 尚未实现或受限 / 下一步**。验收重点包含误匹配、误合并、跨版本污染、错误正式版推荐、完整文件字节保真、失败隔离与成本可观测性。

## 明确非目标

旧数据迁移、旧代码兼容、历史 PR 的功能保持、编辑原始 Bib、独立复查状态机、正文事实支持性审查、学术推荐引擎、自动抓取 Google Scholar 页面以及没有来源的自动改写。
